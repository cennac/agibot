# MiniCPM-V 4.7-35B-A3B：RK3588 实测记录

日期：2026-10-15，Asia/Shanghai。用户要求试用更大的 35B-A3B，并记录 token 测试。

## 模型与路线

准确模型为 `openbmb/MiniCPM-V-4.7-35B-A3B`：总参数约 35B，每 token 激活约 3B，
文本骨干是 `qwen3_5_moe_text`，40 层、每层 256 个专家、每 token 使用 8 个专家。
激活参数量不等于全量权重内存占用，不能直接套用 1B 的 W8A8 常驻转换流程。

本次验证官方混合量化 GGUF + CPU，以及 LES（Lookahead Expert Scheduling，
从磁盘读取专家并提前预取）。这是板端可行性测试；不代表已经完成 35B 的 RKLLM
NPU 转换。66 的现有 GPU 服务保持运行。

官方资源：

- [MiniCPM-V 中文说明](https://github.com/OpenBMB/MiniCPM-V/blob/main/docs/minicpm_v4dot7_zh.md)
- [官方 GGUF](https://huggingface.co/openbmb/MiniCPM-V-4.7-35B-A3B-gguf)
- [官方 LES 说明](https://github.com/OpenBMB/llama.cpp-omni/blob/main/docs/les/lookahead-expert-scheduling.zh.md)

| mmproj-model-f16.gguf | 1,119,575,840 | `bff3b688e14c300eca273092c37c50a0ddfcc2054e079af1a0480edeed5d20f1` |

`mix_q3gud_im` 是混合量化，专家张量使用标准 `Q3_K` 格式。官方 Apple 设备的
速度不能作为 RK3588 的测试结果。61 号记录中“最小约 20 GB、完全无法运行”
的说法应限定为当时所选 Q4 全常驻方案，不适用于这次的混合量化和 LES 尝试。

## 板端环境与编译

板子：`192.168.88.89`，Armbian aarch64，RK3588（4×A76 + 4×A55），15 GiB
内存，7.8 GiB zram swap，228 GB eMMC；实验开始时约 212 GB 磁盘可用。
模型目录 `/root/models/minicpmv47-35ba3b/`，测试目录 `/root/bench35b/`。

官方 LES 源码：`/root/llama.cpp-omni-les`，commit
`0b74404c9b3dfe2c6b11aebe0dd58fc23f133ee2`。

先取得该版本，并把项目 `tools/rkllm/patches/` 复制到 `/root/bench35b/patches/`：

```bash
git -c http.proxy=http://192.168.88.128:7897 clone --depth 1 \
  https://github.com/OpenBMB/llama.cpp-omni /root/llama.cpp-omni-les
git -C /root/llama.cpp-omni-les checkout 0b74404c9b3dfe2c6b11aebe0dd58fc23f133ee2
git -C /root/llama.cpp-omni-les apply /root/bench35b/patches/llama-omni-les-linux-fnocache.patch
git -C /root/llama.cpp-omni-les apply /root/bench35b/patches/llama-omni-les-experts-verify-handles.patch
```

若未来 main 的浅克隆不含该 commit，需要先显式 fetch 此版本。随后编译：

```bash
cmake -S /root/llama.cpp-omni-les -B /root/llama.cpp-omni-les/build \
  -DCMAKE_BUILD_TYPE=Release -DGGML_NATIVE=ON -DLLAMA_CURL=OFF \
  -DLLAMA_BUILD_TESTS=OFF -DLLAMA_BUILD_EXAMPLES=OFF -DLLAMA_BUILD_SERVER=ON \
  -DGGML_CUDA=OFF -DGGML_METAL=OFF
cmake --build /root/llama.cpp-omni-les/build --target llama-mtmd-cli llama-cli -j 6
```

该 fork 没有 `llama-server` 构建目标；应使用它实际提供的 `llama-cli`。
首次编译遇到 Linux 没有 `F_NOCACHE`，已增加宏条件保护；补丁保存为
`tools/rkllm/patches/llama-omni-les-linux-fnocache.patch`。
运行设 `LLAMA_MOE_F_NOCACHE=0`；本补丁没有实现 Linux 的绕过页缓存功能。
两项 CLI 编译完成，日志末尾为 `OMNI_BUILD_OK`。

官方 `tools/moe/experts.py verify` 还存在句柄缓存变量覆盖问题：`experts` 先是
字典，随后变成文件句柄，再执行 `experts[file] = experts`，触发
`TypeError: '_io.BufferedReader' object does not support item assignment`。
把缓存字典单独命名为 `expert_files` 后重跑完整字节校验；修复不改模型、布局或计算。
补丁为 `tools/rkllm/patches/llama-omni-les-experts-verify-handles.patch`。
复现时应先在该固定版本源码上应用这两个补丁，再编译和执行预处理。

## 测试方法与复现入口

脚本放在项目级 `tools/rkllm/`：

- `prepare_35ba3b_les.sh`：提取 expert-major 文件、完整字节验证、生成常驻 GGUF。
- `download_35ba3b.sh`：代理下载与断点续传，校验官方 SHA256 后才改为最终文件名。
- `run_35ba3b_les.sh`：CPU LES 测试入口，使用完整 GGUF + `--no-mmap`。
- `bench_35ba3b.py`：每项独立进程，有超时；保存 stdout/stderr 和 `results.json`。
  从 C++ slot timing 获取实际 tokenizer token 数及速度，每 0.5 秒采样 VmRSS/VmHWM。
  同时采样 VmSwap 和 `/proc/<pid>/io` 的磁盘读取字节数；快速退出前的尾部采样可能
  不完整。峰值内存是进程 RSS，不等同于整个系统页缓存占用。

统一测试参数：CPU 4 线程、context 2048、batch/ubatch 128、seed 42、temperature 0、
关闭 thinking、关闭 warmup、生成上限 64 token。短答可能提前 EOS，实际 token 数以日志为准。
测试中文自我介绍、可核对的水箱算术题，以及宇航员/月球/绿色瓶子图片描述。
这三项是冒烟与可行性测试，不能据此认定全面质量优于其他模型。

LES 保留训练时每 token 8 个专家，不设置 `--moe-k-prefill/decode`。
使用 shared prefill bank 256，decode window 24，lookahead depth 8。
fork 帮助文本把 slot bank 写成“每层”，实际 qwen35moe 实现有共享 prefill bank
和各层 decode 缓存，应以源码与实际分配日志为准。

该 fork 的 CPU backend 没有提供 `alloc-only` buffer 接口，不能直接照搬 Apple 上
精简常驻 GGUF 的装载路径。本次优先用完整 GGUF 保留专家元数据，关闭 mmap；
模型加载器会把虚拟专家从 `weights_map` 移除，只分配专家槽并读取非专家权重。
精简 GGUF 仍作为预处理产物留存。Linux 实际运行能力与报错以最终测试为准。

将上述脚本复制到板子 `/root/bench35b/`，依赖 `aria2c`、
`python3` + numpy，以及前述已编译的官方 fork：

```bash
bash /root/bench35b/download_35ba3b.sh
bash /root/bench35b/prepare_35ba3b_les.sh
MINICPM35_RESULTS=/root/bench35b/les-cpu64 \
  bash /root/bench35b/run_35ba3b_les.sh
MINICPM35_RESULTS=/root/bench35b/les-cpu-math-short \
  bash /root/bench35b/run_35ba3b_les.sh --cases math_short
```

结果目录和专家输出目录必须是新的，防止覆盖旧实验。未手动清理 Linux page cache，
各题独立加载进程，但后续题可能命中系统文件缓存；不能把它们当作严格冷启动对比。

## 实测结果

两份官方文件已通过下载器 SHA256 校验，最终文件大小均与表中相同。
专家提取于 22:22:41 开始；修正验证脚本后，`verified 120 tensors (metadata and bytes)`
通过；22:31:12 输出 `LES_PREPARE_OK`。提取的专家数据为 13,841,203,200 字节，
精简 GGUF 约 1.55 GiB（613 个非路由专家张量）。

首轮测试 22:31:18 开始，CPU + LES，生成上限 64 token：

| 测试 | 提示 token | 提示处理 | 生成 token | 生成速度 | 全程墙钟 | 峰值 RSS | 结果 |
|---|---:|---:|---:|---:|---:|---:|---|
| 中文介绍 | 22 | 16.36 s | 42 | 2.30 tok/s | 49.64 s | 3.21 GiB | 完整回答、正常退出 |
| 算术，普通提示 | 37 | 10.33 s | 64 | 3.59 tok/s | 39.15 s | 3.62 GiB | 额度截断，未输出最终答案 |
| 图片，1024×640 原图 | 335 | 607.10 s | 39 | 4.61 tok/s | 632.44 s | 4.31 GiB | 主体正确，品牌识别错误 |
| 算术，一行提示（补充） | 38 | 5.95 s | 16 | 4.62 tok/s | 23.56 s | 3.62 GiB | `12分钟`，正确 |

介绍输出：

> 我是 MiniCPM 系列模型，由面壁智能（ModelBest）和 OpenBMB 开源社区开发。
> 我致力于提供高效、轻量且强大的 AI 能力，帮助您解决各种问题。

普通算术提示触发了分步解释，64 token 在“8 - 3 = 5”附近耗尽；不能将这项计为
答题正确。关闭 thinking 不会强制正文简短。补充使用 `math_short` 提示，明确要求
只输出一行算式和答案，仍保留同一生成上限。首项 VmSwap 峰值约 0.35 GiB，
第二项为 0；采样到的实际存储读取分别约 9.46 GB、5.24 GB。这些结果不能仅用
进程 RSS 推断系统总占用，文件页缓存仍占用大量可回收内存。

原始 1024×640 图片的默认预处理产生 5 个视觉块。第一、第二块分别耗时约
125.5 s、119.4 s，CPU 图像编码代价很高；不能把文本生成速度当作带图响应速度。
5 块图像处理时间合计 598.87 s；完整提示处理 607.10 s，文字生成仅 8.46 s。
从启动独立进程到退出为 632.44 s，约 10 分 32 秒。图片项 VmSwap 峰值为
0.76 GiB，采样到的实际存储读取约 9.87 GB。

图片原文输出：

> 一名宇航员正悠闲地坐在月球表面，脚踩印有喜力（Heineken）标志的冷藏箱，
> 手中拿着一瓶啤酒，背景是浩瀚星空和地球。

主体场景正确，但图中瓶子与箱子的品牌是 **Carlsberg（嘉士伯）**，不是回答中的
Heineken（喜力）。不能把这项描述记为细节全对，更不能仅凭模型变大宣称识图无误。

补充算术输出：

> (60-0)÷(8-3)=12分钟

补充项于 22:43:21 开始，约 23.56 s 完成；生成 16 token，解码 3.46 s，4.62 tok/s。
4 项进程全部正常退出、未超时，两个结果目录均输出 `BENCH_OK`。该标记表示运行与
指标采集成功，不表示人工质量评价全对。最后一题使用已被前面测试预热过的文件缓存。

## 结论与证据

这块 15 GiB RK3588 **可以通过官方混合量化 + CPU LES 运行 35B-A3B**，保留原始
8 专家路由。当前短文本生成约 2.30–4.62 tok/s；峰值进程 RSS 4.31 GiB，另有
最高约 0.76 GiB 的进程 swap，且依赖大量可回收文件页缓存。首次独立加载、提示处理
和生成各有开销，不能用解码速度直接估计首字延迟。

默认高清输入的带图响应约 10.5 分钟，主要瓶颈是 5 次 CPU 视觉编码，不适合当前
配置下的实时看图。更低分辨率、减少切片或其他视觉加速路线本次未实测，不能填入
推测速度。不同预处理和后端下，也不能把这里的数据与 1B NPU 数字当作严格同条件比较。
本次没有完成 35B RKLLM/NPU 转换，66 上通过的一键转换仍针对文档 64 的 1B。

模型、专家文件、精简 GGUF 和编译目录留在板子，全部测试进程已退出，结束时内存
约 268 MiB used、15 GiB available，swap 约 28 MiB。原有 1B 部署保持原样。
